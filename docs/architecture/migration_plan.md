- `docs/v2_results.json` — сохранённые public-измерения и рецепты; `docs/handoff_verification.json` — последний сохранённый успешный прогон 23 проверок. Это не новый прогон при составлении плана.

## 1. Что хотим получить

Пять независимых функциональных компонентов: Task Understanding, Evaluation, Search, Execution, Publishing. У каждого — проверяемый вход/выход и собственные тесты. Конкурсный запуск остаётся единым `python solution.py task.md`; тяжёлое обучение исполняется в ограниченных subprocess. Сетевые серверы, Kubernetes, брокер сообщений и отдельные базы в эту миграцию не входят.

Границы сервисные, но размещение пока локальное. Это обеспечивает независимость внутренней реализации при сохранении контракта, а не обещание отсутствия любых межкомпонентных зависимостей. В будущем можно заменить транспорт, не меняя смысл сообщений, если для этого появится реальная необходимость.

В Execution различаются три ответственности:

1. **Sampling** — выбор/повторение существующих строк, сжатие дубликатов, under/oversampling.
2. **Weighting** — изменение вклада ошибок, без необходимости менять число строк.
3. **Augmentation** — создание синтетических/искажённых обучающих примеров: masking, позднее SMOTENC.

Операции объединяются в один явно описанный `DataPolicy`, но реализуются отдельно. Политика обязана учитывать общий эффективный вес, а не независимо усиливать редкий класс каждым способом.

## 3. Git: как отделить эксперимент от рабочей версии

```text
main @ 5dd6b0f                       # Проверенная версия
  └─ experiment/modular-augmentation # Интеграционная экспериментальная ветка
       ├─ refactor/contracts-task-evaluation  # Pro
       ├─ refactor/execution-data-policy     # Plus A
       └─ refactor/runtime-build-ci          # Plus B
```

В текущей подготовке создана только интеграционная локальная ветка. Три дочерние ветки — предлагаемые, ещё не созданы. До начала командной работы капитан отдельно разрешает публикацию экспериментальной ветки и подтверждает общий base SHA. Все три участника используют свои клоны; не пишут параллельно в одну директорию.

Правила:

- Рабочие PR направляются в `experiment/modular-augmentation`, не в `main`.
- Один PR — один логический шаг; архитектурный перенос и изменение алгоритма не смешиваются.
- Общие контракты сначала согласуются с их потребителями. Большие изменения не интегрируются одним непроверенным merge перед сдачей.
- После этапа контрактов интегратор фиксирует общий checkpoint SHA; участники начинают совместимую реализацию от него. Ранние unit-тесты можно писать параллельно по fixtures согласованного контракта.
- Интеграция только с review и пройденными gate; main не получает ничего автоматически.
- Не делать force push общих веток и разрушительные откаты. Неудачный PR отменяется отдельным revert либо не включается в следующий release.
- Для публикации работающих checkpoint предполагаются теги: `modular-v3.0.0-alpha.1` (noop parity), `.2` (data-policy API), `.3` (проверенные политики). Это предложения, не созданные теги. Для baseline достаточно уже сохранённых commit и ZIP; новый тег на main без отдельного решения не создаём.
- При выпуске фиксируются commit, версии контрактов/компонентов, SHA сборки, данных, разбиений и политики. Код генерации признаков и ответы planner также входят в идентичность эксперимента.

Старые `docs/parallel_work.md` и `docs/prompts/` описывают прежнее распределение по корневым файлам и функциональное расширение v3. Для этой миграции они не дают права разным владельцам одновременно переписывать одни файлы. Перед запуском реализации обновить задания по этапам этого плана; ранее начатые изменения участников сначала сверить по SHA/диффу, не отменять вслепую.

## 4. Этапы и критерии выхода

### M0 — baseline и воспроизводимость

Владелец: Plus B, review Pro. Рабочий ML-код не меняется.

- Проверить старый ZIP, требования и локальную среду; повторить 23 старые проверки.
- Создать отдельные неизменяемые task-копии и эталонные split manifests для сравнения. Исходные CSV не изменять и не коммитить.
- Сохранить два вида эталона: фиксированные рецепты/сохранённые planner-ответы для parity и полный обычный запуск для проверки жизненного цикла.
- Согласовать бюджет времени/API для benchmark: лимит 600 ₽ общий для команды, не для каждого участника.

**G0:** baseline воспроизводится, известны SHA и ограничения окружения; есть команды запуска и счётчики времени/RAM. Если нет доступа к исходным данным, fixtures-тесты продолжаются, но public parity и promotion блокируются.

### M1 — контракты и characterization tests

Владелец: Pro; оба Plus проверяют удобство потребления.

- Описать TaskSpec, DatasetRef, SplitPlan, ExperimentRequest, DataPolicy, PredictionBundle, EvaluationResult, SelectionPlan.
- Зафиксировать реальный legacy-инвентарь файлов: сейчас CSV/NPZ/JSON, а не обещанный универсальный `predictions.npy`. Старый семиэлементный `discover` возвращает `(spec, profile, train, test, sample, text, hashes)`.
- Определить явные порядок строк/классов/целей, positive class, формат вероятностей, направление метрики и статусы ошибок.
- Массивы и таблицы передавать по immutable refs с хешами, не как гигантский JSON. Никаких pickle для обмена.
- Начать со схемы draft `0.1`; после review и fixtures зафиксировать v1. Совместимые расширения — minor, несовместимые — major; для draft не обещать стабильность, которой ещё нет.
- Добавить проверки неизвестной версии, несовпадения split/data hash, переставленных строк/классов, ошибочной размерности и недопустимых значений.

**G1:** три владельца согласовали fixtures и API; API-клиент не нужен для unit/contract tests. Схемы не содержат бизнес-логики или импортов конкретных моделей. Получен общий checkpoint для последующей параллельной реализации.

### M2 — доказать конкурсную упаковку на маленьком вертикальном примере

Владелец: Plus B, до переноса всего проекта в src.

- Проверить, что структуру разработки можно собрать в ZIP из корневых `.py` плюс исходный requirements, до 100 MB.
- Если требуется преобразование импортов, оно ограниченное, автоматическое и тестируемое: уникальные имена, запрет неоднозначных/dynamic imports, проверка subprocess entry points и обращений к ресурсам через `__file__`.
- Не включать JSON/YAML-конфиги, файлы схем, данные или веса как новые обязательные ресурсы ZIP. Необходимые определения входят в Python-модули; runtime-артефакты создаются уже при запуске.
- Сохранять manifest отображения исходных файлов в модули сборки и SHA вне конкурсного ZIP.
- Проверять импорт и CLI из новой распакованной папки, без checkout в PYTHONPATH, установленных проектных пакетов или editable install.

**G2:** вертикальный пример работает после распаковки. Если сборщик слишком рискован, не блокировать архитектуру: временно сохранить независимые prefixed root-модули и отложить красивое дерево каталогов.

### M3 — разделить существующий агент без смены алгоритма

Pro, Plus A и Plus B работают параллельно в согласованных границах:

- **Pro:** Task Understanding и Evaluation сначала оборачивают старые discover/split/metrics без новых эвристик. Исправление MAPE, новые time/group и произвольные файлы — отдельные функциональные PR позже.
- **Plus A:** Execution возвращает прогнозы и fit metadata; не пишет официальный CSV и не решает, какой кандидат лучший. Изолировать пять существующих backend, не потерять ExtraTrees/linear_text. Backend сам нормализует параметры и описывает capabilities. Search-подпись формируется из эффективного рецепта и версии backend.
- **Plus B:** тонкий orchestrator, Qwen gateway, общий ResourceBudget, process executor, artifact store и Publishing. Единственный Publisher владеет финальным `submission.csv`; каждый эксперимент имеет свой run/experiment ID. Модельные ветвления и список движков не дублируются в prompt и worker.
- Legacy wrappers временно сохраняют CLI и необходимые API. Старые тестовые проверки не ослаблять ради зелёного результата; изменение внутренних patch points допустимо только с сохранением исходной проверяемой семантики и отдельным review.
- Новый DataPolicy пока тождественный: sampling=identity, augmentation=noop, duplicate weighting=off, **class weighting ровно как в v2**. `noop` не отключает уже работавшие веса классов.

**G3 — noop parity:** 23 старые проверки и новые contract/architecture tests пройдены; одинаковые фиксированные рецепты и split дают те же labels/order и близкие числовые прогнозы. Начальная числовая проверка `rtol=1e-6, atol=1e-8`; изменение class decisions разбирается отдельно, а не скрывается допуском метрики. Нет ухудшения качества, которое объясняется изменением поведения. Рост времени/RAM более 10% — повод расследовать и согласовать, не статистическое доказательство по одному запуску. Упаковка и полный жизненный цикл проверены.

Реальные новые ответы Qwen стохастичны и не подходят для строгого parity: для него используются сохранённые ответы/фиксированные рецепты. Отдельный реальный API-прогон доказывает интеграцию, но не идентичность качества.

### M4 — добавить DataPolicy API с безопасными реализациями

Владелец: Plus A; Pro отвечает за отсутствие утечки, Plus B — за выбор/лимиты/учёт в Search.

Контракт преобразования возвращает DatasetRef, targets, sample weights, признак synthetic, происхождение строки (список родителей при синтезе), group/time metadata и manifest. ID исходного test не является входом синтетического генератора. Синтетический sample ID не выдаётся за настоящий ID объекта.

Первые реализации, каждая отдельным PR:

1. `identity/noop`: не менять состав данных и метки; не мутировать общий dataset.
2. Управляемые class weights: сохранить v2 как baseline; добавить explicit source counts, нормализацию и ограничение относительного веса.
3. Мягкое duplicate weighting: группы по признакам, без target/ID; множитель `m^(-beta)` при `beta=0/0.5/1`. Сначала без физического удаления.
4. Сжатие одинаковых пар `(features, label)` с сохранением кратности; не заменять конфликтную feature-группу одной majority-меткой. Сжатие сохраняет вклад в loss, но не обязано сохранить модель из-за row-count hyperparameters — это отдельный эксперимент.
5. Random undersampling крупных классов с контролем разнообразия и сохранением редких объектов.
6. Умеренный Random Oversampling; без шумовых возмущений, никакого равнения всех классов на крупнейший.
7. Masking допустимых признаков в копиях fitting-строк; до imputation, без изменения target/ID. Применимость определяется семантикой TaskSpec, а не хардкодом public-столбцов.

Для каждого метода определить допустимый этап pipeline: общего «любая аугментация после любой предобработки» нет. SMOTENC требует train-only подготовки расстояний; masking — обработки создаваемых пропусков. Обученные преобразования на validation/test только применяются, строки там не добавляются и не удаляются.

**G4:** все новые методы выключены по умолчанию; проходят тесты provenance, повторяемости, допустимости схемы, веса, ограничений роста и отсутствия внешних validation labels. Ошибочная политика не превращается в молчаливый успех: сохранить статус/причину и использовать разрешённый baseline fallback.

### M5 — измерить пользу политик, а не объявлять её

Сначала замороженная модель/рецепт, одинаковые исходные fold IDs и бюджет. Все числа ниже — стартовые диапазоны гипотез, не оптимальные параметры.

| ID | Изменение относительно явного контроля | Начальная настройка |
|---|---|---|
| D0 | Контроль v2 | identity + noop, прежняя class_weight_power |
| D1 | Только мягкие веса классов | power 0.25/0.5/0.75, тест cap отношения 20 отдельно |
| D2 | Только влияние дубликатов | beta=0.5; при необходимости 0/1 |
| D3 | Только размер крупных классов | сохранить 85%, затем 70%; редкие не сокращать |
| D4 | Только повторение редких | 1.5x, затем 2x; без полного уравнивания |
| D5 | Только missingness robustness | копии 10–25% fitting-строк; masking 5–15% допустимых наблюдаемых значений; вес копии 0.3/0.5 |
| D6 | Сочетание лучших D1–D4 | только после отдельных результатов, общий effective-weight budget |

Не запускать полный декартов перебор этой таблицы. Сначала один вариант на политику, затем 1–2 настройки перспективного направления. Для доказательства вклада ограничителя веса или масштаба нужна соответствующая отдельная абляция. В частности, смена power и включение cap одновременно не доказывает пользу cap.

При сравнении resampling заранее фиксируется class-weight rule и источник counts. Автоматический пересчёт весов после изменения числа строк может частично отменять resampling или непреднамеренно усилить его — этот выбор входит в policy manifest.

Внешняя validation остаётся исходной с естественными пропорциями. Сначала выделяются исходные fold-группы, затем каждая политика обучается только на fitting-части, включая новый fit на каждом inner split. Родители synthetic/duplicate объектов не пересекают границу fold. Full refit повторяет выбранный метод только после отбора на валидации.

Для classification сохранять Macro F1 и per-class precision/recall/F1 с числом объектов, особенно уникальных групп редкого класса. Для regression — RMSE и срезы по пропускам. Дополнительно: время, peak RAM всего запуска, размер артефактов, количество исходных/производных строк и расход API.

**G5:** направление улучшения подтверждено минимум на двух допустимых разбиениях, нет необъяснённого обвала классов/ресурсов; результаты на уже исследованном public не называются независимым private test. Если результат неоднозначен, остаётся контроль/noop; отсутствие выигрыша — нормальный исход эксперимента.

### M6 — только затем более рискованные стратегии

Отдельные добровольные PR после G5 и при наличии времени:

- SMOTENC на смешанных данных: k=3/5, достаточно уникальных соседей; исключить неоднозначные/недопустимые источники генерации по явной политике, не удаляя автоматически оригинальные данные. Проверить категориальные и физические ограничения. Для чисто категориальных данных это не подходящий метод.
- Balanced subset ensemble: 2–3 модели на разных сокращённых majority-подвыборках, редкие примеры сохраняются; усреднение вероятностей и явный бюджет refit. Это отдельная ансамблевая стратегия Search, не transform одной таблицы.
- Осторожная псевдоразметка: отдельный teacher/student сценарий Search, не обычный Augmenter; доступ к немеченому test только по разрешённой политике. Не использовать confidence как доказательство истинности меток.
- Новое понимание задач/time-group/multi-target/ranking остаётся важным самостоятельным направлением из вебинара, но не смешивается с PR чистой миграции или оценкой аугментации. Неподдерживаемые типы должны получать честную диагностику, а не имитацию успеха.

CTGAN/диффузии, новые зависимости, облачные GPU, LLM-генерация меток и агрессивная nearest-neighbour очистка не входят в обязательный scope миграции.

### M7 — финальный gate и решение капитана

- Проверить фактическую новую сборку после распаковки: CLI, отсутствие локальных исходников в import paths, секретов, данных и весов.
- Проверить 8 CPU, 32 GB RAM, 30 GB диска и общий deadline до 3 часов с запасом на refit/export. Учитывать управляющий процесс, дочерние процессы и размер артефактов, не только память одного worker. Полноценную OS security sandbox не обещать без отдельной проверки возможностей среды.
- Проверить API fail/429/timeout, malformed JSON, падение worker/refit, конфликт выходных файлов, finite probabilities и корректное восстановление рабочего checkpoint.
- Сохранить сравнение v2 → modular noop → modular selected policy. Архитектурный эффект и изменение обучения видны отдельно.
- Капитан решает: оставить эксперимент в ветке, разрешить merge в main или запросить доработку. Submit требует отдельного явного согласия, автоматически не выполняется.

**G7:** известны точные SHA кандидата и ZIP, все обязательные проверки выполнены, ограничения задокументированы. Ни зелёные unit-тесты, ни чистота архитектуры сами по себе не являются доказательством более высокого score.

## 5. Границы ответственности трёх участников

| Владелец | Свои каталоги/задачи | Независимая проверка |
|---|---|---|
| Pro — самая сложная семантика | contracts, task_understanding, evaluation, fixtures метрик и разбиений, антиутечка | Plus A/B как потребители API |
| Plus A — исполнение и политики данных | execution, model_adapters, sampling/weighting/augmentation, их unit tests | Pro проверяет корректность, Plus B — integration |
| Plus B — жизненный цикл и интеграция | search, publishing, infrastructure, bootstrap, tools, CI/architecture tests | Pro/A проверяют соответствующие границы |

На переходном этапе изменения старых корневых файлов согласуются отдельно: один файл в один момент — один владелец. Pro не переписывает worker, Plus A — runner, Plus B — metric implementation без согласованной передачи. В contracts запрещены скрытые зависимости от backend, API-клиента или оркестратора. Тест импортов запрещает доступ к внутренностям соседнего компонента; взаимодействие через api/contracts.

Ожидаемый первый результат от каждого: маленький PR, тест и пример сообщения, а не полное самостоятельное переписывание всего проекта. Большие задачи Pro не означают единоличного утверждения своих контрактов.

## 6. Автоматические проверки и экспериментальный журнал

На каждый PR — offline unit, consumer/provider contract, import-boundary, совместимость v2 и распакованная synthetic-сборка. Реальный Qwen/public benchmark — отдельный контролируемый запуск; секреты не выдавать недоверенным PR. План не утверждает, что branch protection/CI уже настроены: это задача Plus B, доступность функций GitHub проверяется при настройке.

Каждый результат сохраняет:

```text
experiment_id / run_id / git SHA:
contract + backend + data-policy versions:
data SHA / source split SHA / inner split SHA:
recipe SHA / transform code SHA / seed:
class counts before/after / duplicate groups / effective weights:
original/derived rows / provenance manifest:
metric control -> candidate / per-class results:
wall time / process-tree + controller RAM / disk / Qwen usage:
keep / discard / failed / inconclusive:
reason / known limitations:
```

Измерения сравнимы только при понятной методике. Переход random → group/time не объявляется ухудшением качества из-за нового числа: корректность разбиения и сравнение моделей на одном и том же разбиении — отдельные вопросы.

## 7. Откат и ограничение риска

- До G3 любые новые sampling/augmentation выключены. До G5 новые политики не становятся default.
- Неудачную политику можно выключить через DataPolicy, сохранив независимую архитектуру; архитектурные и алгоритмические PR не склеиваются.
- Если сам перенос ухудшает стабильность/качество или не успевает пройти gate, конкурсная рабочая версия остаётся v2 из main/сохранённого ZIP. Не удаляем эксперимент ради отката.
- Не используем `reset --hard` и force push для коллективного rollback. До merge main не нуждается в откате; после merge — отдельный reviewed revert при необходимости.
- Feature freeze определяется капитаном по подтверждённому дедлайну. При нехватке времени завершаем последний зелёный checkpoint, а не добавляем синтетические генераторы перед сдачей.

## 8. Что делаем следующим, если план принят

1. Получить разрешение на публикацию **только экспериментальной ветки**, main не трогать.
2. Подтвердить актуальные SHA работы трёх участников и отсутствие параллельного редактирования одних файлов.
3. Выполнить M0 и согласовать M1; Plus B параллельно делает маленький packaging spike M2.
4. После общего checkpoint выдать обновлённые три задания и начать M3.
5. Включать преобразования данных только после доказанной noop parity.

Источники инженерных правил: [маленькие логические изменения и topic branches в Git](https://git-scm.com/docs/gitworkflows), [SemVer](https://semver.org/). ML-основания и ограничения сохранены в `docs/data_audit.md`, `docs/v2_validation.md`, `docs/webinar_20261021.md`; эти документы не являются доказательством ещё не выполненных экспериментов с аугментацией.
