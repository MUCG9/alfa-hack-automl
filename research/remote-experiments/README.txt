Два компьютера, одна исследовательская очередь Alfa AutoML

Диспетчерская ветка: research/remote-dispatch. Разработка основного кода: work/night-research-20261023. Ветки обновляются обычным fast-forward push; main/force push не используются. Единственный диспетчер — главная задача; рабочий агент не переписывает эту ветку.

Сейчас transport-status.json явно показывает готовность транспорта. Пока status!=ready, рабочий агент только периодически читает готовность. Эта папка и промпт не означают, что второй агент уже подключился или что тесты уже прошли. Первое подключение подтверждается фактической claim-веткой; результат — проверенным result-пакетом.

Папки:
- jobs/: неизменяемые READY задания JSON, которые появляются только после готовности исходников и протокола. Не изменять опубликованный job, включая draft->ready; для новой попытки нужен новый ID с сохранением старого исхода.
- sources/: проверенный код, source manifests, контрольные рецепты, SHA и ссылки только на десять публичных файлов организаторов. Данных/прогнозов/весов/ключей здесь нет.
- results/: полученные сводные результаты и указатели на исходные immutable Git result refs; статус remote-reported сам по себе не квалифицирует качество.
- reviews/: решения главного агента и границы проверки, привязанные к job/result/source hashes.
- hypotheses/: следующие гипотезы по измеренным результатам; каждая должна получить отдельный протокол до fit.

Git-ветки пакетов:
research/remote-claims/JOB — атомарная заявка одного исполнителя на неизменяемый job.
research/remote-results/JOB — неизменяемый sealed результат, привязанный к claim/job/dispatch SHA.
Пакеты содержат только свой маленький tree и имеют объявленный parent. Повторная доставка возможна только для того же пакета; это не повторное обучение.

Цикл главного агента: проверить результаты -> проверить исходники/метрики/лимиты и причины неудач -> сформировать следующую гипотезу -> опубликовать неизменяемый READY job -> продолжать независимое локальное исследование. Цикл второго агента: poll -> claim -> один ограниченный опыт -> независимый аудит -> submit -> poll. Каждый использует штатный периодический запуск в своей задаче, без системных служб и дополнительных платных ресурсов.

Процесс можно распараллелить между этими двумя компьютерами. Внутри каждого компьютера один training job за раз; ресурсы и реальные часы отдельного job задаются до запуска. Секреты и закрытые учётные данные не передаются через Git. Публичный результат содержит source patch и агрегаты; private данные, split files, predictions, weights и сырые логи сохраняются только у исполнителя. Новые числа считаются remote-reported до независимой проверки/подтверждения. Новый релиз требует отдельного полного стандартного запуска/refit/CSV/gates; ни component gain, ни полученный JSON не отправляются на платформу автоматически.

Первый job remote-port-01 готовит переносимый kernel harness и решение Windows Unicode/joblib проблемы без model fits. Последующий ML job будет отдельным после source review, с теми же пятью срезами и сильным fresh control. Главный компьютер тем временем готовит полноценную проверку L1.

Запуск второго агента: прочитать REMOTE_AGENT_START.txt. Детали CLI и точная JSON-схема отчёта появятся в transport-README.txt вместе с прошедшей проверку версией инструмента. Наличие GitHub-доступа на втором компьютере не проверяется заранее главным агентом; capability report обязан честно сообщить отсутствие прав/автоматизации/зависимостей.
