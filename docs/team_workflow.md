# Предварительная рабочая система к встрече 22 октября

> Исторический план пяти участников и двух Pro. Теперь актуален план **один Pro + два Plus** в `parallel_work.md`; он заменяет назначения ниже. Правила вебинара — `webinar_20261021.md`, общий контракт — `v3_contract.md`.

## Что мы создаём

Один Python-агент получает новую ML-задачу, читает её описание и данные, организует собственную валидацию, предлагает и проверяет гипотезы, выбирает лучший результат и сохраняет `submission.csv`. Его код повторно запускают на неизвестных задачах. Сильная модель на двух публичных таблицах полезна, но ещё не доказывает универсальность агента.

Работа с ИИ ускоряет написание кода. Наше преимущество нужно проверять экспериментами: одинаковый split, точная метрика, воспроизводимые изменения и быстрые безопасные объединения. Согласованные промпты помогают удерживать эти условия. Длина промпта сама по себе не является критерием успеха.

## Пять владельцев результатов

Капитан занимает один из пяти слотов. Pro-участники обозначены P1 и P2, реальные имена назначаем на встрече. Это распределение ответственности, а не запрет другим помогать с кодом.

| Участник | Основная зона | Что отдаёт команде за первые 24 часа | Кто проверяет |
|---|---|---|---|
| P1, GPT Pro | архитектура, orchestration, интеграция, восстановление после ошибок | агент с deadline, best checkpoint, журналом Qwen и устойчивым запуском | P2 |
| P2, GPT Pro | независимый технический разбор, честная валидация, универсальность/private, текстовые данные | тесты на неизвестной схеме, text recipe, проверка метрик и критика архитектуры | P1 + профильный ML-владелец |
| P3, ML | регрессия | 4–6 ablation-экспериментов на одном split, recipe и время fit | P2 |
| P4, ML | классификация | Macro F1, per-class F1, class weights, дубликаты и категориальные значения | P2 |
| P5, AI/аналитика | спецификация, общий контекст, промпты, журнал решений и бюджет | версия общего контекста, 5 согласованных заданий, сравнительная таблица результатов | капитан |

P1 и P2 получают наиболее объёмные задачи, потому что у них есть Pro. Их разделяем на автора и независимого проверяющего. P2 не утверждает собственные изменения единолично. Капитан принимает release/submit-решения вне зависимости от того, какой слот занимает.

## Владение файлами

- P1 владеет `solution.py`, `agent_runner.py`, `agent_worker.py` и сборкой ZIP. Он интегрирует recipes из PR других участников.
- P2 владеет `agent_core.py` и тестами валидации; text-изменения worker согласует с P1.
- P3 исследует регрессионные recipes и передаёт проверенные изменения секции `agent_policy.py` / `model_utils.py` через P1.
- P4 аналогично исследует классификационные recipes. P3/P4 не правят один общий файл параллельно без согласования.
- P5 владеет `program.md`, `docs/prompt_pack.md`, протоколом встречи, реестром уточнений и сводкой результатов.

Это обновлённое распределение по фактической структуре v2. Отдельные recipe-модули пока не созданы и не требуются для параллельных экспериментальных веток. До интеграции P1/P2 согласуют контракт функций. Только корневые `.py` и исходный `requirements.txt` входят в ZIP. Markdown и тестовые данные остаются в рабочем репозитории.

## Цикл работы

1. P5/капитан записывает issue: гипотеза, один изменяемый фактор, acceptance criteria.
2. Исполнитель передаёт ИИ `program.md`, общий контекст и task prompt из `prompt_pack.md`.
3. Исполнитель запускает код и сохраняет факт: split hash, metric, время, память, исключения.
4. Независимый участник проверяет diff и воспроизводит результат.
5. P1 интегрирует изменение и прогоняет обе публичные задачи.
6. Капитан решает, тратить ли один из трёх submit-слотов.

Завершённая задача содержит commit/артефакт и проверку. Ответ ИИ «готово» без запуска не считается выполнением.

## Общий экспериментальный контракт

Каждая запись содержит:

```json
{
  "experiment_id": "CLS-004",
  "context_version": "2026-10-21-v1",
  "data_hash": "...",
  "split_hash": "...",
  "metric": "macro_f1",
  "baseline_experiment": "CLS-001",
  "hypothesis": "...",
  "one_changed_factor": "...",
  "metric_before": 0.0,
  "metric_after": 0.0,
  "wall_seconds": 0,
  "peak_rss_mb": 0,
  "qwen_tokens": 0,
  "verdict": "keep/reject/inconclusive",
  "commit": "..."
}
```

Значения 0.0 в шаблоне — placeholders, не результаты. Нельзя называть локальную метрику баллами leaderboard. Среднее по одному holdout не является cross-validation mean/std.

## Ритм до сдачи

На встрече подтвердить фактический дедлайн. Текущий рабочий план относительно встречи:

- Сегодня, 21 окт: прочитать уточнения, проверить первую версию и её ограничения.
- Завтра, 22 окт: 60–75 минут на решение по архитектуре, ролям, split и первой версии ZIP.
- Первые 24 часа после встречи: P3/P4 измеряют recipes, P1/P2 закрывают надёжность и private, P5 ведёт контекст.
- Следующие 24 часа: интеграция проверенных изменений, локальный регрессионный прогон и первый осмысленный submit.
- За 24 часа до реального дедлайна: feature freeze. Только исправления критических ошибок, воспроизведение и финальная сдача.

## Повестка встречи на 65 минут

| Время | Обсуждение | Решение |
|---:|---|---|
| 0–10 | что оценивают и что уточнили организаторы | единые правила |
| 10–20 | демонстрация v1 → v2, реальные запуски и ограничения | исходная версия для команды |
| 20–30 | фиксированный split, метрики, private text | policy оценки |
| 30–40 | пять владельцев, Pro-задачи, границы файлов | имена и review-пары |
| 40–50 | общий контекст и промпты | один источник текущих решений |
| 50–60 | backlog и submit-стратегия | ближайшие 24 часа |
| 60–65 | открытые вопросы и deadline | decision log |
