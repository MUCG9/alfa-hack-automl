# Проверка v2: методология и ограничения

Дата: 21.10.2026, MSK. Вопрос: стала ли новая версия надёжнее и сильнее v1 на доступных задачах, чтобы оправдать следующий submit? Это инженерная проверка кода и локальных метрик, не прогноз официального балла.

## Исходная точка

Неизменённый отправленный `solution-v1.zip`, SHA-256 `dda94ac5073327140870a2f29550e50e9b841ea2937b3a9b8317b7037470aba8`, повторно запущен точной командой платформы `python solution.py task.md`, с настоящим Qwen и параметрами по умолчанию. Внешний контроль фиксировал время, память и завершение процессов.

| Задача | Локальная метрика v1 | Время агента | Финальное обучение |
|---|---:|---:|---|
| Регрессия, RMSE ↓ | 43.6158776 | 126.937 с | успешно |
| Классификация, Macro F1 ↑ | 0.6156390 | 1264.726 с | успешно |

Это новый повтор поиска, а не восстановление приватных логов платформы. Ранее были получены другие локальные результаты: 43.60655 / 0.60358 и 43.68225 / 0.61898. Qwen и поиск стохастические, один удачный запуск не гарантирует такой же рецепт при submit.

## Что могло привести к слабому баллу

Подтверждено кодом/запусками:

- маленький стартовый портфель и узкие параметры;
- `depth` не влиял на LightGBM, а row subsampling при `subsample_freq=0` не работал;
- stopping по loss вместо целевой Macro F1;
- балансировка классов только вкл./выкл., без мягкого промежуточного веса;
- усечение некоторых ответов Qwen до появления JSON;
- отсутствие полноценного наследования, подтверждения рецепта и проверенного смешивания;
- один holdout одновременно участвовал в stopping и выборе рецепта.

Не доказано: какой из этих факторов снизил официальный score и на сколько. Организаторы подтвердили выполнение двух задач, но не предоставили отдельные метрики, baseline для нормирования и логи. Успешное завершение не означает высокое качество. Последний увиденный рейтинг 8.5774 и карточка 857.742 — разные отображения; объяснение их масштаба отсутствует. Не выводим из этой разницы ошибку модели.

Одинаковые public-данные и search split seed 42. В этом разделе stopping мог использовать search holdout специально для воспроизведения v1; результаты нельзя смешивать с nested-режимом как одну CV.

| Работающий row subsampling | RMSE 43.42836 | улучшение в этой абляции |

Nested-followup (stopping уже внутри fitting rows): RMSE 42.91538 без нового feature-кода, 42.82004 с предложенными Qwen признаками; Macro F1 0.63860 с мягкими весами и 0.64865 с отдельными Qwen-взаимодействиями. Это exploratory-результаты, не окончательные показатели упакованной версии.

## API Qwen: отдельный воспроизводимый дефект

Один запрос на review исчерпал 14 000 completion-токенов, все — reasoning, финальный JSON отсутствовал. В контрольном прогоне запрос планировщика исчерпал 16 384 токена за 209.724 с без JSON. На том же proxy проверены две настройки:

| Настройка | Время | Reasoning tokens | Итог |
|---|---:|---:|---|
| `reasoning: {enabled: false}` | 3.508 с | 0 | корректный JSON, 362 completion tokens |
| `enable_thinking: false` | 10.966 с | 1342 | JSON есть, но thinking фактически не отключён |

Это отдельные запросы, не статистическое исследование latency. Первая настройка проверена повторно на review кода: 34.240 с, 3043 completion tokens, reasoning 0. В production добавлена она, а не неподтверждённый флаг. При отказе шлюза по HTTP 400 предусмотрена одна попытка совместимости в том же deadline. Внутренние рассуждения модели не сохраняются.

Полный прогон также выявил бесполезные попытки Qwen обращаться к target внутри feature-кода. Физически target туда не передаётся, но guarded-код мог стать no-op. Контракт усилен списками разрешённых/запрещённых столбцов и явным `params.log_target`; такие обращения теперь отклоняются до обучения.

Ещё одна проверка выявила повторение Qwen одних и тех же рецептов, несмотря на запись неудач в большом контексте. Точное dedup не дало повторно обучить их, но обращения API тратились зря. Проверена связка более компактного feedback-first контекста и temperature 0.4: две новые конфигурации за 6.665 с, 642 completion tokens и 0 reasoning tokens. Это единичный тест новизны, не доказательство роста метрики или преимущество одной только temperature. В production измеренные исходы теперь стоят перед справочной информацией; полный код лучшего рецепта сохраняется. От повторов по-прежнему защищает dedup и детерминированный fallback.

## Финальный протокол

- v1 и v2 получают одинаковые public CSV, команду запуска и search split seed 42.
- В v2 inner split seed 73 выбирает stopping/пороги только по fitting rows.
- До трёх лучших кандидатов перепроверяются на seed 43 при достаточном времени; рецепт выбирается по среднему двух метрик. Ensemble принимается только при улучшении этого среднего.
- После фиксации рецепта проводится дополнительная проверка на seed 44 без поиска и без использования внешних меток при обучении. Эти метки физически вынесены из папки задачи worker.
- Это не полностью независимая оценка: все строки public уже участвовали в исследовании команды, а seed 42/43 используются для выбора. Не называем их blind test или полным 5-fold CV.
- Для классификации с большим числом дубликатов split группирует точные хеши признаков; в public нулевое пересечение. Регрессионный random split содержит одинаковые признаки по обе стороны и требует отдельной оговорки.
- Хеши данных, task и исходников контролируются до/после. Финальный ZIP должен побайтно совпасть с замороженным snapshot полного прогона.

## Проверки надёжности

Unit и end-to-end проверяют: реальные параметры глубины/row subsampling, наследование/JSON, F1/AUC, веса, отказ от cross-row statistics и файлового I/O, unseen categories, вероятностные контракты, порядок классов ensemble, API timeout, сохранение checkpoint при провале refit, отсутствие влияния внешних target-меток на log-transform, старые результаты и provenance. Synthetic smoke проверяет переименованную регрессию, числовые метки, новые категории и длинный текст.

Ограничения: Python-процесс и AST-фильтр не являются полной security sandbox; поддерживаются CSV, один target и один ID; смысл положительного класса при единственном вероятностном столбце предполагается по второму строково-отсортированному классу. Для временных/пользовательских групп нет гарантированного автоматического извлечения grouping из произвольного текста. Text проверен только на synthetic. Все зависимости файла requirements целиком локально не переустанавливались: проверялся используемый кодом поднабор с заданными версиями и Python 3.12.
