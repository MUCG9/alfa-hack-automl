# Промпты для совместной работы

Версия общего контекста: `2026-10-21-v1`. Перед каждым заданием участник передаёт ИИ общий блок, актуальные исходники своего модуля, issue и результаты предыдущих проверок. Ключ API в эти промпты не вставляется. Сначала обновляем общий контекст, затем меняем задания, которые зависят от обновления.

## 0. Общий блок для всех

```text
Мы участвуем в Alfa Hack AutoML. Создаём универсального Qwen-агента, который
читает task.md и train/test/data_dictionary/sample_submission, сам выбирает
валидацию, генерирует и выполняет код, проверяет гипотезы и сохраняет лучший
submission.csv. Код должен работать на новых приватных текстовых/табличных задачах.

Правила: Python 3.12, 8 CPU, 32 GB RAM, 3 часа на каждую задачу.
В ZIP передаются только корневые .py и оригинальный requirements.txt.
mcp не установлен. Сеть только через прокси организатора. OPENAI_BASE_URL,
OPENAI_API_KEY и OPENAI_MODEL берутся из окружения. Нельзя устанавливать пакеты
из скрипта или скачивать данные/модели из сети. В финальном запуске доступен Qwen.
600 ₽/сутки относятся только к разработке, не к проверке на платформе.

Public: regression site_eui/RMSE и attack_cat/Macro F1. Private неизвестен.
Эти имена разрешены в текущем runtime-разборе, но нельзя зашивать их в оркестратор.
ID не признак. Split и evaluator фиксируются до экспериментов.
При class duplicates сравниваем group-by-feature-hash и stratified validation.

Работай только по заданному issue и границам своего модуля.
Не меняй интерфейсы без отдельного предложения интегратору.
Ни один вывод о качестве без запуска и артефактов не считается фактом.
Не называй локальный holdout score баллами leaderboard.
Результат: изменение кода, команда запуска, фактический вывод, риски, следующий тест.
Если проверка недоступна, явно пометь её как невыполненную.
```

## 1. P1 Pro: архитектура и интеграция

```text
Ты отвечаешь за orchestration и интеграцию первой версии. Прочитай solution.py,
agent_worker.py и контракт agent_core.py. Найди реальные точки потери результата:
LLM timeout, невалидный JSON, авария worker, deadline, финальное обучение,
неправильный путь и перезапись best.

Реализуй smallest useful patch по issue. Сохрани ранний валидный submission,
атомарную замену и recovery. Ключи не должны попадать в worker или trace.
Добавь только проверки, которые воспроизводят риск по issue.
Проверь запуск через python3 solution.py task.md с модулями из корня ZIP.
Покажи actual logs, длительность и что ещё не проверено.

Не переписывай ML-recipes соседних участников. Если нужен новый интерфейс,
предложи сигнатуру и миграцию как отдельное решение капитану.
```

## 2. P2 Pro: независимая валидация и private

```text
Ты независимый технический проверяющий. Не исходи из правильности кода или
заявленных результатов. Проверь target/id inference, направление метрики,
leakage при preprocessing, split и selection bias от многократных гипотез.
Проверь известные classification feature-дубликаты и редкий Worms.

Создай маленькие задачи с другими именами target/id, неизвестными категориями,
пропусками, числовыми labels и длинной текстовой колонкой. Запусти тот же агент.
Для текста предложи CPU-рецепт на TF-IDF и линейной модели из разрешённых пакетов,
без предобученных embeddings и без сети.

Верни воспроизводимые дефекты с severity, минимальные тесты и конкретные patch.
Отдельно укажи, какие public-улучшения могут ухудшить private.
Не меняй evaluator ради улучшения метрики.
```

## 3. P3: регрессия

```text
Проведи 4–6 сопоставимых экспериментов по regression recipe на одном split hash.
Сохрани исходную шкалу RMSE. Проверь бустинги, missing indicators, разумные
агрегаты, log1p target с обратным преобразованием. Меняй один фактор за раз.
Не передавай target и id в генерацию признаков. Не вычисляй статистики с target
по всей train до split. Сравни хотя бы одно временное/group ограничение как
диагностику устойчивости, не смешивай его score с основной таблицей.

На выходе: recipe-функция в согласованном корневом модуле, таблица экспериментов,
RMSE, wall time, peak RAM, split hash, verdict. Не копируй тяжёлый ensemble в агент
без измерения полного времени fit/predict.
```

## 4. P4: классификация

```text
Проведи 4–6 экспериментов на classification recipe. Главная метрика Macro F1.
Отчитай Accuracy, Weighted F1 и per-class F1. Сначала убедись, что split защищён
от feature-дубликатов. Отдельно измерь отличие от обычного stratified split.
Не используй id, в test он пересекается с train. Обработай unseen categories.

Сравни unweighted и balanced, регуляризацию и короткий CPU-бустинг.
Покажи поведение редких классов. Один seed/holdout не называй CV.
Верни корневой recipe-модуль по контракту, фактические логи и предложение
следующего эксперимента. Числа без запуска не заполняй.
```

## 5. P5: контекст, prompts и память агента

```text
Ты отвечаешь за общий контекст команды и память Qwen-агента. Прочитай актуальные
правила, task schema, последние результаты и decision log. Найди противоречия
между промптами участников и передай владельцам конкретные поправки.

Сделай короткий runtime-prompt: задача, разрешённые действия, неизменный split,
последние гипотезы/результаты, оставшееся время, формат JSON следующего действия.
Промпт должен приводить к проверяемой гипотезе и минимальному коду признаков.
Добавь обработку невалидного JSON/обрезанного ответа. Не сохраняй секреты и
не отправляй Qwen полные CSV или гигантские логи.

Верни версию prompt, пример входа/выхода, фактическую проверку через API,
токены/расход и таблицу изменений относительно предыдущей версии.
```

## 6. Общая проверка перед merge

```text
Проверь этот diff как независимый reviewer. Ищи только конкретные ошибки,
которые способны испортить метрику, воспроизводимость или запуск на платформе.
Проверь контракт, target leakage, schema drift, deadline, NaN/inf, категории,
семантику метрики, зависимости и плоский ZIP.

Для каждой находки дай файл/строку, воспроизведение, влияние и минимальный fix.
Если блокирующих находок нет, перечисли реально выполненные проверки и пробелы.
Не считай сообщение автора о прохождении тестов доказательством без логов.
```

## 7. Промпт капитана для ежедневной сводки

```text
Ниже отчёты пяти участников. Сведи их в один статус: что действительно готово,
что подтверждено метриками на одном split, какие изменения конфликтуют,
кто блокирует интеграцию и какой один следующий результат у каждого.
Не усредняй разные split/метрики. Раздели факты, гипотезы и решения капитана.
Предложи один осмысленный platform submit с ожидаемым сигналом, если все
обязательные проверки пройдены. Слот не расходуй сам без согласованного порядка.
```
